**1. 优先修复：连续压缩会覆盖此前摘要，已确认要求会从模型输入中消失。**

代码位置（以下 Python 路径相对同级 `nanobot/` 仓库）：

- `nanobot/agent/memory.py:949`：只取尚未压缩的新片段交给 `archive()`。
- `nanobot/agent/memory.py:1032`：摘要输入来自该片段，没有合并此前 `_last_summary`。
- `nanobot/agent/memory.py:965`：新摘要直接覆盖 `_last_summary`。
- `nanobot/agent/memory.py:1247`、`:1291`：闲置压缩同样只概括当前剩余内容，再覆盖旧摘要。
- `nanobot/agent/loop.py` 的 `Consolidator(store=None, ...)`：普通会话使用这条会话摘要路径。

模拟首先确认“预算150万元；后续以报告_v2.docx为基准；保留新增审批条款”。第一次压缩后这些要求在摘要中。加入新的无关措辞讨论，触发第二次压缩后，生成摘要的请求中已经没有旧摘要；下一轮 ContextBuilder 生成的完整模型输入也没有这些要求。

本例的摘要提供者逐字返回所收到的输入，刻意排除了模型概括不准确的影响。即使摘要模型没有遗漏任何收到的文字，框架仍然会丢掉第一段摘要。消息窗口模式下原始记录可能仍在持久化文件中，但不再进入常规模型输入；闲置压缩还会缩短活动会话的消息列表。

120 是消息条数，包含工具调用与工具结果，不是 120 次用户对话。文档处理中一次用户请求可以消耗多条消息，因此该问题可能早于用户直觉中的“超长会话”出现。闲置压缩默认配置为 15 分钟，是否实际触发取决于部署配置与运行状态。

**2. 优先修复：普通 Word 修改没有明确的基准版本与交付内容约束。**

代码位置：

- GUI `src/core/nanobot-client.ts:576`：普通消息没有文档 ID、基准 revision 或源内容哈希字段；已有 presentation 与专家团队修订字段属于专用流程。
- GUI `src/core/sessionArtifacts.ts:179`：产物按修改时间排序、按同一路径去重，这是列表展示逻辑。
- `nanobot/storage/state.py:4477`：`supersedes_artifact_id` 只在相同 `relative_path` 下寻找前一版本。`报告_v1.docx` 和 `报告_v2.docx` 不会自动组成同一文档的版本链。
- `nanobot/agent/tools/docx.py:59`：按模型提供的源稿路径生成文件。
- `nanobot/agent/tools/docx.py:345`：校验文件存在、大小、可打开、有正文，没有校验基于哪个版本、保留哪些已确认条款。

实际文档故障注入如下：

1. v1：预算 100 万，没有审批条款。
2. v2：预算 150 万，增加“付款前须书面审批”。
3. 本轮指令：“只在最新的报告_v2.docx对应源稿上，把标题改为‘年度项目报告’，输出报告_v3.docx；预算150万元和新增审批条款必须保留，禁止退回v1。”
4. 脚本模拟模型选错基准：通过真实 AgentLoop 调用计划工具、读取 v1 源稿、写出基于 v1 的 v3 源稿、调用 `create_docx`、完成计划并回复。

捕获的模型请求完整包含本轮指令。运行时仍接受这组调用，返回的附件包含真实 `报告_v3.docx`。重新打开 Word 检查正文，标题已更新，预算是 100 万，审批条款缺失。

这证明：文件生成成功不等于修订要求兑现。错误的模型选择能够直接变成正常交付。这里没有使用真实模型来决定选哪个版本，不能把模拟的错误选择归因于某个模型。

**3. 需要调整：本轮消息尾部重复旧指令，且“上一轮证据”可能遗漏最近产物。**

`nanobot/agent/context.py:162` 将旧用户请求、助手回答片段和工具参数生成证据索引；`:172` 取前 20 次工具调用；`:177` 再从头截到 6,000 字符；`:670`、`:680` 将其附在当前用户文字后面。索引中的工具结果只提取 HTTP(S) URL，不专门提取本地产物文件路径。

因此，当一轮里先读旧稿、最后生成新稿时，靠近当前请求的索引可能突出旧稿而省略新产物。完整历史仍然存在，不应把它描述为所有最新产物信息都被删除。代码也明确把这块标为历史证据、不是新指令；这能减轻混淆，但当前顺序和截断方式仍有不必要的干扰风险。

本次没有发现最新用户原文在所测 GUI 传输和 AgentLoop 输入路径中被旧消息直接替换。所谓“最新指令权重”不能通过这次静态检查解释成某个数值权重设置错误。已证实的是：有效历史约束会丢失、最新文档基准没有被明确保存和校验、旧要求会重复出现在本轮消息尾部。

**建议的修复顺序与验收条件。**

1. 修复两类压缩的摘要累积：把旧摘要和新增历史共同归纳，保留仍有效的约束、已被撤销的要求与明确的版本关系。连续多次压缩、闲置和重启后，已确认要求必须仍可恢复。
2. 在 nanobot 保存普通文档的逻辑 ID、当前基准版本、源稿与 Word 的对应关系；本轮明确绑定用户指定的基准。执行时校验基准版本或哈希，生成后记录父版本。用户明确指定旧版时允许有意分支；不能仅凭全项目文件修改时间推断“最新版”。
3. 调整上下文：最新要求与历史证据清楚分隔；历史证据优先保留最近成功的产物与有效约束，避免重复大段旧工具参数；明确处理新旧要求冲突。
4. 增加文档修订验收：对“只改标题”“保持其余内容”做内容差异核对；对预算、日期、表格、必留条款等检查结果。内容核对失败不能仅凭 DOCX 可打开就报告成功。
5. 用实际内网模型运行多轮评测：覆盖连续三版修改、同会话多文档、显式切回旧版、附件换版、压缩后的继续修改和外部编辑。测量基准选择与修改要求兑现率，独立于模型接口连通率和文件生成成功率。
