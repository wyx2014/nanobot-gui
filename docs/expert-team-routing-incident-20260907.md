## 原因

`clarify` 路由使 gateway 抑制当前轮团队、不给它创建运行 ID，也不注入团队专属 MCP。AgentLoop 随后进入普通 Agent 分支。原有“只追问，不规划和调用工具”仅通过上下文提示表达，普通 Agent 仍拿到了原生工具，并自行开始投研。

因此，数据源偏差是错误路由及其执行隔离缺失的后果。这次记录不支持“先尝试金融 MCP 失败，再降级网页搜索”的解释。

路由器原先只有 220 Token 输出额度，并用 `json_repair` 接受不完整 JSON；`run` 缺失 `target` 又被转换成 `clarify`，混淆了模型输出异常和用户确实缺少标的。历史日志没有保存该次模型原始路由响应及 reason，无法确认当时是语义误判还是响应不完整。同模型、同句子的现场复查能返回正确 `run`，不能把截断当作已证实的历史根因。

## 修复

- 路由提示明确：公司名足以启动研究，证券代码、投资期限等可以在后续解析，不能据此要求重复确认。
- 输出额度改为 512 Token；不完整/不合法结果或首次 `clarify` 最多再复核一次，额度为 1024 Token，仍受外层总超时约束。只接受完整 JSON 或完整 JSON 代码块，不修补残缺结果。
- 缺少目标的 `run` 属于无效路由。路由不可用时提示稍后重试，不再静默转交普通 Agent，也不将其记为等待用户提供标的。
- `clarify` 由 AgentLoop 直接返回提示，不调用通用模型执行循环、不创建计划、不调用搜索或其他工具。真正无关的请求仍可通过显式 `bypass` 走普通聊天。
- 路由日志记录 reason；复核日志记录尝试次数、结束原因和结果有效性，便于区别语义判断与输出截断。

原有固定流程和数据源约束继续由运行时执行：基础数据包 → 四角色并行 → Team Lead → 报告审校；核心金融来源优先，公开搜索按已有规则兜底。
