# 定时任务树状页面与运行记录 Spec

## 目标

定时任务页面以「任务」为主对象展示。执行记录从属于任务，不再作为左侧常驻列表占用会话空间。

同时解决手动运行后前端长期显示「执行中」的问题：运行记录必须在任务开始时可见，在任务结束后可靠更新为完成或失败。

## 信息架构

```text
左侧
├─ 新建对话
├─ 定时任务
├─ 工具箱
└─ 项目 / 对话

定时任务页面
├─ 顶部操作
│  ├─ 让TPACowork帮我创建
│  └─ 新建任务
└─ 任务列表
   ├─ 任务 A
   │  ├─ 配置摘要
   │  ├─ 操作：展开记录 / 编辑 / 运行一次 / 暂停启用 / 删除
   │  └─ 展开后显示该任务的执行记录
   └─ 任务 B
      └─ 展开后显示执行记录
```

## 行为

- 左侧只保留「定时任务」入口，不展示定时任务记录树。
- 定时任务页面默认展示任务列表。
- 每个任务可以展开 / 折叠执行记录。
- 任务卡片展示任务名、频率摘要、最近运行时间、记录数量和启停状态。
- 任务卡片 hover 后展示编辑、立即运行、删除等低频操作。
- 点击「立即运行」后自动展开该任务，并短轮询刷新记录状态。
- 页面中存在 `running` 记录时，每 2 秒刷新一次任务列表；没有运行中记录时停止轮询。
- 执行记录必须展示可识别标题：
  - 优先使用对应会话标题。
  - 如果会话标题为空、`新对话` 或 `New chat`，使用 `{M/D HH:mm} - {任务名}`。
- 执行记录展示相对时间、状态和查看会话按钮。
- 执行记录点击「查看会话」进入对应会话；如果本地没有会话，先从 gateway 同步该 session。
- 新建、编辑、暂停、恢复、立即运行、删除仍复用现有定时任务 API。
- 删除任务会同时移除该任务下的执行记录展示，因为记录从属于任务。

## 后端运行记录要求

- `CronRunRecord.status` 支持 `running`、`ok`、`error`、`skipped`。
- 任务开始执行时，先写入一条 `running` 记录并持久化到 `jobs.json`。
- 任务完成、跳过或失败后，更新同一条记录的状态、耗时、错误信息、run id 和 session key。
- 手动运行接口 `/api/schedule/tasks/run` 不等待任务完整执行结束；它只触发后台运行并立即返回当前任务 payload。
- API 输出给 GUI 时：
  - `running` 映射为 `running`。
  - `error` 映射为 `error`。
  - `ok` 和 `skipped` 映射为 `completed`。
  - `running` 记录没有可打开 session 时，不返回伪造会话 key。
- cron 服务加载历史时需要修复异常状态：
  - 超过 24 小时仍是 `running` 的记录标记为 `error`。
  - 如果 audit run 文件已经记录完成状态，使用 audit 信息修复对应 `running` 记录。

## 测试要求

- 后端：
  - 任务开始后、完成前，`jobs.json` 中能看到 `running` 记录。
  - 任务完成后，同一条记录更新为 `ok` / `error` / `skipped`。
  - 重启加载时，陈旧 `running` 记录会变成错误。
  - audit 已完成但 `jobs.json` 仍是 `running` 时，加载后能修复。
- 前端：
  - 手动运行后立即出现执行记录。
  - 后端完成后，页面自动从「执行中」刷新为完成或失败。
  - 刷新应用后，不应把已经完成的记录继续显示为「执行中」。
  - 记录标题不能只显示 `新对话`，应能看出属于哪个任务和哪次运行。

## 非目标

- 不新增独立「记录」Tab。
- 不新增独立后端数据模型；运行状态继续落在 cron job 的 `run_history` 中。
- 不做全局执行记录搜索。任务很多或记录很多时，再补筛选 / 分页。
